# Tech Aim Single Target v1.0 — report and persistence matrix

Written 2026-08-30, at the close of Phase A. Every row below was checked
against current source or a current test run, not against memory.

Two different questions get confused when they share a column, so they have
their own:

- **RELOAD / RECOVERY** — after an interruption (crash, power loss, reconnect),
  does the session come back and continue?
- **COMPLETED RESULT ACCESS** — after a *clean* finish, can the result be
  reached again later?

A cleanly completed session is deliberately **not** offered as a recovery
candidate. That is correct behaviour, not a gap: `closeSession(Clean)` archives
the journal so a finished course can never be presented as an unfinished one.
It is also not the same as the result being reachable, which is why the second
column exists.

## The notes, in full

### ¹ Open Practice has no separate "practice report"

Open Practice and fixed Training sessions produce the Summary and Match
reports, the same two the qualification modes use. There has never been a
distinct practice report, and none was created here. This is **not**
cross-routing: no Final can reach these tabs (`UI-DEC-017`), and these sessions
claim no ISSF course.

**Classification: as designed.** Not a defect, not a limitation.

### ² The `.tch` does not record the shot's role

The `.tch` match file lists shots without saying which were sighters. The
authoritative record — the journal — always has, through separate
`SighterAccepted` and `ShotAccepted` events, and that is what recovery and the
finals reports read.

The consequence is confined to the `.tch`: a file reopened through *Load saved
session* presents its shots as one undifferentiated match.

**Classification: ACCEPTED LIMITATION / POST-v1.0.** Changing the `.tch` schema
is a persistence-format change and is out of scope for a release freeze. It is
recorded here, in the blocker inventory, and in the gate.

### ³ 3P position-change sighters are tagged `(counted)` in the backend

Known, evidenced, and explained in the blocker inventory as item D. Course
interpretation is correct — officials come from `globalMatchModel` — but a
forensic reader has to split by position to get the true count, which is how
the RC3F audit had to be performed.

**Classification: ACCEPTED LIMITATION / POST-v1.0.**

### ⁴ COMPLETED RESULT ACCESS for a Final — PARTIAL, and why

At completion, a Final's result **is** reachable and exportable: the completion
card offers *View Report*, which now opens that Final's own report, and the
report exports a PDF. Both were verified this round — for AR and AP, and by
rendering the real report DTO to a page (see the evidence images).

**Later**, the situation is:

| | |
|---|---|
| The result is persisted | **yes** — the journal is archived under `Sessions/Archive`, and a `.tch` is written |
| It is offered as a crash-recovery candidate | **no, correctly** — a clean close archives the journal precisely so a finished course is never presented as an interrupted one |
| It can be reopened *as a Final* through the application | **NO** |

*Load saved session* on the login page reads a `.tch` and restores a generic
match record. It does not restore `isFinals10mMatch` or `isFinalsMatch`, so a
reloaded Final is presented as a match, through the Match report — with its
sighters undifferentiated (note ²) and none of the Final's series or
single-shot structure.

**Per §19 this is classified as ACCEPTED LIMITATION / POST-v1.0, not a
blocker**, on these grounds:

- v1.0's contract is "the completed result is persisted, and the report can be
  viewed and exported at completion". Both hold, and both are tested.
- A historical completed-result browser was never designed or promised. Building
  one during a release freeze is exactly what §19 forbids.
- The crash-recovery path must **not** be repurposed as a result browser; doing
  so would put finished sessions back into the recovery candidate list, which is
  the one thing the archive behaviour exists to prevent.

**What closing it would require, post-v1.0:** a `.tch` schema that carries the
discipline and the shot role (note ²), and a session-history entry point that
opens an archived journal read-only. Both are real work with a real design
decision behind them. Neither is a report-correctness defect in what v1.0
ships.

### ⁵ The journalled shot time was wrong, and is now right

Found by this round's before/after-reduction comparison (§22). The controller
measured each shot's split correctly for the screen, then `buildShotCore()`
measured it **again** for the journal — after `m_lastAcceptScaled` had already
been advanced. The journal therefore recorded the time between building two
structs, near zero, for every shot.

Nothing an operator saw during a Final was affected; the live record was always
right. What was affected was every **recovered** session and every report built
from one: all shot times came back as 0 s.

The measurement is now taken once and passed to the journal, and the harness
asserts row-by-row that `timeSec` survives reduction unchanged. This is inside
the 10 m finals persistence layer — the same layer as blockers F and G — and
touches no acquisition, scoring or 3P code.

## What the matrix does not claim

- It does not claim any 10 m Final path was physically retested. It was not.
  See `V1.0-PHYSICAL-EVIDENCE-INHERITANCE.md`: the 10 m report path is
  **automated / replay / render validated**, and its physical baseline for
  acquisition is inherited from RC3F.
- It does not claim ranking, placing or elimination for any mode. A single lane
  cannot know them, and every report says so.
