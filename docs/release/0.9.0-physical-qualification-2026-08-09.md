## PROVEN

### RECONNECT-001 — FIXED AND PHYSICALLY VERIFIED

Failure on RC2e: cable unplugged, the application detected nothing, the next
shot was lost, the log stayed silent 4½ minutes while the shooting screen
looked healthy.

Root cause (three compounding, all confirmed in code):
1. `checkForNewShots()` discarded the read's return value; a failed read leaves
   the buffer zeroed and is indistinguishable from "no new shots".
2. The one disconnect check was gated on `m_hardwareCheckDisabled`, which
   **defaults to true**.
3. `ModbusAdapter::m_connected` is a cached bool cleared only on explicit
   disconnect, so `isModBusConnected()` answered true throughout the outage.

Fix on RC2f, verified on hardware:

```
18:01:56.431  target link LOST after 3 consecutive failed reads -
              acquisition suspended, no shots or feeds will be accepted
18:01:56.545  serial scan started: 2 port(s) discovered      <- CH340 absent
              ... 15 controlled attempts at ~2 s, Bluetooth rejected every time
18:02:25.683  serial scan started: 3 port(s) discovered      <- CH340 returned
18:02:25.713  candidate COM4 (USB-SERIAL CH340) score 1150 [remembered target]
18:02:25.844  target link RESTORED on COM4 after 15 attempt(s);
              counter was 1, target reports 1 - adopted as baseline, not replayed
18:03:13.395  decoded x=-4.9 y=-0.3        <- shot after reconnect
18:03:15.020  paper feed completed: shot 2
```

Detection ≈300 ms. Re-enumeration proven by the port count moving 3→2→3.
Session preserved — one journal, no new session. Zero phantom, zero feed during
the outage or on restore. Manual COM selection never required.

### PAPER-FEED-001 / 002 — PHYSICALLY VERIFIED

RC2e, one continuous session:

```
17:31:06  seq 1 (sighter)  x=-2.4 y=5.0   score 9.0   -> fed
17:32:59  seq 2 (sighter)  x=7.6  y=-9.9  score 6.2   -> fed
17:34:26  paper feed: shot numbering reset (shot count reset) - 2 identities cleared
17:34:54  seq 1 (counted)  x=-7.1 y=-6.8              -> fed
17:35:55  seq 2 (counted)  x=2.6  y=-0.7  score 10.1  -> fed
```

The reset is emitted **before** `changeSighterMode` logs its own — the central
`resetShootinCount()` authority firing, not a QML path. Exactly 2 identities
cleared. The counted `seq 1` did **not** collide with the sighter `seq 1`; no
`paper feed skipped` appears anywhere. This is the boundary that failed on
RC2b and RC2c.

### Auto-zoom (QML-SHOT-001) — PHYSICALLY VERIFIED

`zoom-requested` and `zoom-started` on all 9 accepted shots. Zero QML errors
across the day.

### Application latency — MEASURED

Count-seen → marker visible: **189, 201, 202, 216 ms**. No drift. The poll is
100 ms (`TachusWidget::m_timer`), not the 1000 ms `scanRate` — that belongs to
the never-shown QModMaster window.

### Target hardware behaviour — PROVEN BY READ-ONLY PROBE

With Tech Aim **closed**, one shot fired:

```
counter        0 -> 1
shot 1 coords  x=-4.2 y=-4.3  ->  x=-3.8 y=-8.7   (OVERWRITTEN)
```

1. The target detects shots and increments its counter with no software
   running. **Target hardware is healthy.**
2. **Coordinate slot indexing follows the counter.** With the counter at 0 the
   next shot overwrote slot 1. Writing `8193 = 0` therefore causes the target to
   overwrite stored shot coordinates on the next shot. This is a hard
   constraint on any future synchronisation design.

## OBSERVED ONCE

### RESTART-001 — OPEN, SEVERITY 1

**Not fixed. Not closed. Root cause not established.**

Sequence on RC2f:

1. Unfinished session contained exactly two Sighters
2. Application closed normally
3. Application restarted; remembered CH340 reconnected automatically (103 ms)
4. Unfinished-session prompt appeared; operator chose **Resume**
5. Exactly two historical Sighters visible, once each — **recovery display
   correct**
6. Operator fired one additional physical shot
7. **The shot did not register.** No score, no marker, no feed
8. Log silent 3+ minutes; no link loss; reads succeeding

Session journal was **flawless**: `RecoveryStarted(fromSeq 5)` →
`RecoveryCompleted(resumedAtSeq 5, truncatedTail false)`, two `SighterAccepted`,
no duplicates, and no `SighterAccepted` after recovery. **The defect is in
hardware-counter synchronisation, not session recovery.**

**Four reproduction attempts on RC2g-DIAG all produced `ACCEPT`.** The
application zeroes the target counter at every startup, so baseline and target
always agreed at 0 and delta was always exactly 1. The failing condition could
not be created on demand, including after firing with the software closed.

Each was stated with confidence and disproved by measurement. Recorded so they
are not revived.

| Theory | Disproved by |

Five wrong diagnoses in one day, all corrected by physical evidence. The
pattern is consistent: **the log recorded only accepted shots, so every
rejection was invisible and theories could not be tested.** That is what the
new instrumentation fixes.

## Confirmed architectural findings

1. **Shot poll is 100 ms** (`TachusWidget::m_timer`); `scanRate = 1000` drives
   the unused QModMaster table.
2. **Serial link is 19200 baud, Even parity, 8N1-E, RTS disabled** — not the
   9600/None previously assumed.
3. **Modbus access is mutex-serialised**; `MotorThread` does **not** hold the
   lock across the 1.4 s feed, so polling continues during paper movement.
4. **Slot indexing follows the counter** — resetting the counter destroys
   stored coordinates on the next shot.
5. **`isAppDemoMode` means "is LIVE"** — the name is inverted, and it is `1`
   during normal operation, confirmed by diagnostics.
6. All fixes sit in `TachusWidget` / `PaperFeedCoordinator`, the shared
   acquisition path, so every discipline inherits them. No discipline has a
   private acquisition, feed or shot-display path.

## Diagnostic capability added

`ACQDIAG`, behind `developer_mode`, negligible when off:

- raw hardware counter (register 8192), application baseline, delta
- named branch for every outcome: `ACCEPT`, `REJECT_COUNTER_WENT_BACKWARDS`,
  `REJECT_DELTA_TOO_LARGE`
- Modbus return code, connection state, link state, login-page state, live flag
- **acquisition heartbeat ~1 Hz** — proves polling is alive when nothing is
  accepted, the exact evidence missing during the RECONNECT-001 outage
- `resetShootinCount()` entry and readback, previously logged only on failure
- coordinate slot/address, `ShotAccepted`, paper-feed request identity

Plus `tools/probe` — a read-only Modbus RTU probe. It writes no register and
issues no motor command, and it established the two target-hardware facts above
that no log could.

**Recommendation: retain permanently.** RESTART-001 was invisible; it no longer
is. If it recurs the log will name the branch and the numbers at the moment it
happens.
