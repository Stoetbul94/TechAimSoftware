# Tech Aim — shot polling architecture and latency budget

Audit performed 2026-08-08 on commit `78b273e`, offline, no hardware.

> **Headline: the shot poll already runs at 100 ms.** An earlier statement in
> this session attributed the perceived delay to a 1000 ms poll. That was
> wrong, and the correction changes the proposed RC2e scope substantially.

---

## 1. Two timers, only one of which is the shot path

| Timer | Interval | Drives | On the shot path? |
|---|---|---|---|
| `TachusWidget::m_timer` (`tachuswidget.cpp:40-45`) | **100 ms** | `on_pushButton_2_clicked()` → `checkForNewShots()` | **YES** |
| `ModbusAdapter::m_pollTimer` (`modbusadapter.cpp:22-27`) | `scanRate`, default **1000 ms** | `modbusTransaction()` — the vendored QModMaster register table | **No** |

`scanRate` comes from `ModbusCommSettings`, persisted at
`Session/ScanRate` in the ModReader QSettings, defaulting to 1000 ms
(`modbuscommsettings.cpp:342-345`). It feeds the QModMaster window, which is
never shown (`mainWin->show()` is commented out). **Changing it would not
affect shot latency at all.**

## 2. What one shot poll actually does

`TachusWidget::on_pushButton_2_clicked()`, every 100 ms:

1. Guard: return unless live mode, off the login page, hardware not flagged
   disconnected.
2. `checkForNewShots()` → **one** `modbusReadRegistry(8192, 2)` — the shot
   counter.
3. Only if the count increased: **one** `modbusReadRegistry(16376 + 8i, 2)`
   **per new shot** — the X/Y coordinates.

**Steady state (no shot): exactly one Modbus read of 2 registers per 100 ms.**
A shot adds one more read.

## 3. Thread and serialisation

- The poll timer lives on the **GUI thread**; `on_pushButton_2_clicked` is a
  slot, so polling runs in the main event loop.
- Modbus I/O is **synchronous**: `directModbusReadRegistry` calls
  `modbus_read_registers` directly.
- Access is serialised by a mutex:
  ```cpp
  int ModbusAdapter::directModbusReadRegistry(int startAdd, int noOfItems, uint16_t* dest)
  {
      QMutexLocker locker(&m_modbusMutex);
      return modbus_read_registers(m_modbus, startAdd, noOfItems, dest);
  }
  ```
  So there is **no concurrent access to one Modbus context**, and no overlapping
  requests are possible — a second caller blocks until the first returns.
- Because the read is synchronous on the GUI thread, a slow or timing-out
  response **blocks the interface** for the duration of the timeout. That is
  the real risk in this design, not bus saturation.

Qt timers do not accumulate: if a poll is still running when the interval
expires, the next timeout is delivered after the slot returns rather than
queueing up. Polls cannot pile into a backlog.

## 4. Calculated bus time

**Actual link settings, from today's log** — note these differ from the values
quoted in the task brief:

```
17:14:24.786  Srinivas - portname COM4 19200 Even 8 1 Disable 1
```

**19200 baud, 8 data bits, EVEN parity, 1 stop bit** — not 9600/none. With a
start bit, 8 data, 1 parity and 1 stop bit, one character is **11 bits**, so
one character takes 11 / 19200 = **0.573 ms**.

Modbus RTU frame sizes for the operations this application performs:

| Frame | Bytes | Wire time |
|---|---|---|
| Read request (function 3, addr + count) | 8 | 4.58 ms |
| Read response, 2 registers | 9 | 5.16 ms |
| Silent interval (3.5 chars, ×2) | — | 4.01 ms |
| **One complete read transaction** | **17 + idle** | **≈ 13.7 ms** |

**Bus occupancy, steady state (one read per cycle):**

| Poll interval | Transactions/s | Bus occupancy |
|---|---|---|
| 1000 ms | 1 | **1.4 %** |
| 500 ms | 2 | 2.7 % |
| 250 ms | 4 | 5.5 % |
| **100 ms (current)** | **10** | **13.7 %** |
| 50 ms | 20 | 27.4 % |

At the current 100 ms the bus is about **14 % occupied** — comfortable. Even
50 ms would be viable on wire time alone.

> **CALCULATED BUS TIME** above is arithmetic from the real frame sizes and the
> real link settings.
>
> **TARGET FIRMWARE RESPONSE TIME — UNKNOWN WITHOUT HARDWARE.** The figures
> above exclude however long the target takes to turn a request around. Today's
> log shows `isHardwareConnected` taking ~40 ms and ~1000 ms on different
> occasions, and motor status reads taking ~175 ms, which suggests firmware
> turnaround dominates wire time by an order of magnitude. **No poll-rate
> decision should be made on the calculated figures alone.**

## 5. Motor feed interaction

From `tachuswidget.cpp` and today's log, one feed is:

```
write 8196 = 256        (motor on)
write 8197 = duration
write 8198 = 4096       (trigger)
read  8198              -> "Reading motor status -> started"
... ~1 s ...
write 8196/8197/8198    (stop sequence)
read  8198              -> "Reading motor status -> stoped"
```

Observed: `Send motor movement signal` 17:33:54.4 → `completed` 17:33:55.75,
**≈1.4 s**, of which ~1.0 s is the configured `motor_movement_time`.

Key points:

- The motor runs on `MotorThread`, a **separate thread**.
- It does **not** hold the Modbus mutex for the whole 1.4 s. Each register
  write and status read is an individual mutex acquisition, and the wait between
  start and stop happens **outside** the lock.
- Therefore **shot polling continues during paper movement**, interleaving with
  the motor's writes. A shot arriving mid-feed can still be detected.
- The mutex prevents frame interleaving on the wire, so bus corruption is
  prevented by construction.

**Not yet verified without hardware:** whether the *target* accepts a shot-count
read while its motor is running, and whether a shot landing during paper
movement is registered correctly. That is a physical question.

## 6. Where the latency actually is

Budget for one shot, from the measured RC2d evidence:

| Component | Time | Source |
|---|---|---|
| Target acquisition + counter update | **UNKNOWN** | not measurable without hardware |
| Poll wait (0–100 ms, avg 50) | ≤ 100 ms | 100 ms timer |
| Counter read + coordinate read | ~27 ms calculated, more in practice | wire + firmware |
| `decoded` → marker visible | **188 ms** | measured |
| **Application total** | **≈ 240–290 ms worst case** | |

An operator perceiving "half a second to a second" against an application
contribution of ~250 ms means **the majority of the delay is upstream of the
application** — in the target's own acquisition and counter update — or the
perception overestimates a genuine but smaller delay. Both are common; neither
can be separated without measurement.

## 7. Recommendation

**Do not change the poll rate.** The evidence does not support it:

- the poll is already 100 ms, not 1000 ms;
- application-side contribution is ~250 ms worst case, of which only ≤100 ms is
  the poll — halving it saves ≤50 ms, which nobody will perceive;
- the read is synchronous on the GUI thread, so polling *faster* increases the
  chance of the interface stalling on a slow firmware response;
- the dominant term is unmeasured.

**Measure first.** The next physical test should record shot-to-display on
phone video (240 fps if available) and compare it against the `decoded` →
`qml-marker-added` stamps already in the log. That splits total latency into
"before the application" and "inside the application" with real numbers. Only
then is there a basis for changing anything.

If a change is eventually justified, the safer design is **completion-driven
scheduling** — schedule the next poll after the previous one returns, rather
than running a fixed timer faster — plus moving the synchronous read off the GUI
thread. Neither is warranted by today's evidence.
