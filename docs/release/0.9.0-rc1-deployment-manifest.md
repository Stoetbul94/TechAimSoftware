## How it was deployed

`tools/release/build-rc1-package.ps1` copies an explicit **allow-list** out of
the build tree — never `release/` wholesale, which also holds object files,
moc/qrc output, the developer `config.ini` and, during a review, capture data.

### windeployqt deviation — recorded, not hidden

`windeployqt` from `C:\Qt\6.5.3\mingw_64\bin` **fails on this machine** with
`Unable to find the platform plugin`, even though
`plugins/platforms/qwindows.dll` is present. It was run from the package
directory, from the Qt `bin` directory, and with `--plugindir` given
explicitly; it resolved the module set correctly every time and then failed at
the plugin step.

The packaging script therefore **runs windeployqt first and records the
outcome**, and falls back to an explicit allow-list when the platform plugin is
absent afterwards. The allow-list is **not a guess**: the Qt module set is
exactly what windeployqt itself reported under *"To be deployed"*, and the QML
modules are the imports found in the repository's `.qml` files.

This is a **deviation from the instruction to use windeployqt** and is recorded
as such. The resulting package is audited file by file, which windeployqt's
output is not.

## Data locations (AppData, not the portable folder)

Mutable data is **never** written inside the portable folder, so the ZIP can be
extracted read-only or to a shared location and two installations cannot
overwrite each other's data.

Root: `%LOCALAPPDATA%\TechAim`

| Purpose | Path |
|---|---|
| Settings | `%LOCALAPPDATA%\TechAim\Settings` |
| Logs | `%LOCALAPPDATA%\TechAim\Logs` |
| Active sessions | `%LOCALAPPDATA%\TechAim\Sessions\Current` |
| Completed sessions | `%LOCALAPPDATA%\TechAim\Sessions` |
| Recovery journals | `%LOCALAPPDATA%\TechAim\Sessions\...\*.jsonl` |
| Derived indexes | `%LOCALAPPDATA%\TechAim\DerivedIndexes` |
| Exported reports | `%LOCALAPPDATA%\TechAim\Exports` · `\Reports` |
| Crash diagnostics / support bundles | `%LOCALAPPDATA%\TechAim\SupportBundles` |
| Backups | `%LOCALAPPDATA%\TechAim\Backups` |

`%LOCALAPPDATA%` is per Windows user, so two users on one machine keep separate
data by construction. Two *installations* under the same user share the one
AppData root — that is intended, so a session started under one copy is
recoverable under another.

An isolated root can be forced with
`--documentation-capture --data-root <absolute path>`; that profile **refuses
to run in Live mode** and is not used by the field test.
