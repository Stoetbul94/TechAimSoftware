## Part 1 — serial device detection

### Current architecture (confirmed)

| | |
|---|---|
| Enumeration | `QSerialPortInfo::availablePorts()` — `ModReader/forms/tachuswidget.cpp:149`, `ModReader/src/mainwindow.cpp:122,832` |
| Connect entry | `TachusWidget::connectedModbus(QString portName)` — `tachuswidget.cpp:100` |
| Transport | libmodbus RTU — `modbus_new_rtu(port, baud, parity, dataBits, stopBits, RTS)`, `modbusadapter.cpp:41` |
| Defaults | **9600 baud · 8 data bits · parity None · 1 stop bit · RTS Disable** (`modbuscommsettings.cpp:282-305`) |
| Persisted identity | `RTU/SerialPort`, `RTU/SerialPortName` — **COM name only** |
| In-session memory | `m_lastManuallyConnectedPort` — **process lifetime only** (`tachuswidget.h:445`) |
| Safe identity probe | **None.** `tachuswidget.cpp:145` records that `isHardwareConnected()` "blocks indefinitely on an open port with no responding target" |

### Root cause — AUTOMATIC COM DETECTION — FAIL

Two defects at `tachuswidget.cpp:148-167`:

1. **The fallback only runs when the port field is empty** (`if (portName.isEmpty())`). Once any port has been configured, auto-detect never executes.
2. **When it does run it opens every serial port in enumeration order and keeps the first that opens.** No VID, PID, serial number, manufacturer or description is examined.

On Arnold's laptop enumeration order is COM4 (CH340), COM5 (Bluetooth), COM6
(Bluetooth). Opening a Bluetooth serial port normally *succeeds* even with no
device behind it, so the "first that opens" rule can select COM5 and then wait
forever for a Modbus reply.

No stable fingerprint is stored, so a target returning on a different COM
number after re-plugging is unrecognisable.

### Regression case for the mock provider

| Port | Description | Expected |
|---|---|---|
| COM4 | USB-SERIAL CH340 | **SELECTED** |
| COM5 | Standard Serial over Bluetooth link | rejected |
| COM6 | Standard Serial over Bluetooth link | rejected |

## Part 2 — automatic paper feed

### Current architecture (confirmed)

| | |
|---|---|
| Motor command | `MotorThread::run()` — `tachuswidget.h:39-45`: `startMotor()` → `QThread::msleep(duration*1000)` → `stopMotor()` |
| Register | `modbusWriteSingleRegister(8196, 32768)` starts the motor (`tachuswidget.h:50`), with a bounded status poll |
| Public API | `TachusWidget::initiateMotorMovement()` — `tachuswidget.cpp:1107`, guarded by `isModBusConnected()` |
| Durations | `motor_movement_time`, `motor_movement_time_sighter` in `config.ini` (`appsettings.cpp:39-40`), pushed via `setMotorMovementTime(match, sighter)` |
| Manual feed | `ShootingPage.qml:661` → `MODREADER.initiateMotorMovement()` |
| Shot acceptance | `emit shootCountChanged(...)` — `tachuswidget.cpp:326,426`; **single shared handler** at `CenterPane.qml:252 onShootCountChanged`, used by both hardware and demo |

### Root cause — AUTOMATIC PAPER FEED — FAIL

**Automatic feed is disabled at the shot-acceptance path and survives only as a
view side effect.**

- `CenterPane.qml:346` — the call on the shot-acceptance path is **commented
  out**, directly above a comment reading *"for issue -> Auto feed not working
  #76"*. This is a previously known, deliberately disabled feature.
- `CenterPane.qml:594`, `1764` — two further commented-out calls.
- `CenterPane.qml:917` — the **only live** automatic call, inside a **ListView
  delegate**, gated on `disableMotorMovement` / `autoMotorMovementMode`.

A delegate is the wrong place for a hardware command. Delegates are created and
destroyed by the view on scrolling and model reset, so a motor command attached
to one can fire late, fire twice, or never fire. That is consistent with what
Arnold observed: manual feed works, automatic feed does not.

### Sighter duration is accepted but never used

`setMotorMovementTime(time, sighterMotorTime)` (`tachuswidget.h:168-173`)
stores `m_motor_movement_duration_sighter` but passes **only the match time**
to the thread. `MotorThread` holds a single `motor_movement_time`. So even if
automatic feed were re-enabled today, **a sighter would feed for the match
duration**.

### What a fix must therefore provide

- One central post-acceptance coordinator in **C++**, driven by the shot-
  acceptance authority — never a QML delegate.
- Per-shot-type duration selection (sighter vs counted).
- Duplicate suppression keyed on shot identity, so one accepted shot yields
  exactly one motor command.
- Serialisation while the motor is running.
- Hard exclusions: rejected/malformed/duplicate shots, recovery replay,
  historical loading, report generation, Demo mode, reconnect probing, and
  `duration == 0`.
