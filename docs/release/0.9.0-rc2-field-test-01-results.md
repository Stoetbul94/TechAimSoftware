## SERIAL-AUTO-001 — Severity 2 — ROOT CAUSE PROVEN

**Physical target not automatically selected; manual COM4 selection works.**

### Evidence — the operator's own field log

`%TEMP%\tachus_log01082026-145445.log`, the RC2 session:

```
Backend 14:54:48.164 -> connect with port number -> Auto Connect
Backend 14:54:48.187 -> Auto connecting to port number -> COM4
Backend 14:55:28.582 -> connect with port number manually -> COM4
Backend 14:55:28.606 -> Auto connecting to port number -> COM4
```

**Not one RC2 selector line appears anywhere in the log.** Searching the whole
file for `serial scan started`, `candidate`, `auto-connect attempted`,
`remembered target`, `target not detected` and `manual selection required`
returns **zero matches**.

The COM4 at 14:54:48.187 is **not** the selector's choice. It comes from
`MainWindow::modbusConnect` (`mainwindow.cpp:688`):

```cpp
if (portName.isEmpty())
    portName = m_modbusCommSettings->serialPortName();   // stored ModReader setting
```

### Failed stage: 5 — CANDIDATE APPLICATION

Not enumeration, not Bluetooth rejection, not ranking, not fingerprint
matching. **The selector never executed at all.**

`TachusWidget::connectedModbus()` still does this, in order:

1. substitute `m_lastManuallyConnectedPort` if the argument is empty;
2. return early if already connected;
3. **`changedConnect(true, portName)` with the still-empty name** — which
   substitutes the *stored* port and opens it;
4. `if (isModBusConnected()) { ... return true; }`
5. **`if (portName.isEmpty()) { ...RC2 selector... }`** ← only reached if 4 failed

Step 3 fires a connection attempt on the stored port **before** the selector is
consulted, and step 4 returns on success. The RC2 selector is therefore dead
code at startup on any machine that already has a stored port — which is every
machine that has ever connected once.

That also explains the shape of the field session: the startup attempt used the
stored COM4 and did not establish working communication, and because step 4's
result short-circuited the function the selector never got its turn. Arnold's
manual COM4 entry at 14:55:28 took the ordinary manual path and worked.

### What this is NOT

- Not a ranking bug — the ranking was never invoked.
- Not a Bluetooth-filter bug — COM5/COM6 were never examined.
- Not a fingerprint bug — nothing was ever stored, because remembering happens
  only after a *selector-driven* successful connection.
- Not a QSettings bug — `HKCU\Software\TechAim` has no `TargetDevice` group,
  exactly as expected when the selector has never run.

### The fix, when authorised

Consult the selector **before** the speculative stored-port connect, and treat
the stored port as one more candidate rather than as a pre-emptive action. The
selector itself needs no redesign — it was never reached.

**No code has been changed.** The brief requires the failed stage to be
identified first; it now is.

## Instrumentation — what exists and what is missing

| Event | Timestamped today? |
|---|---|
| Target frame received | ❌ missing |
| Modbus data accepted | ⚠️ only via the coordinate line, no explicit accept |
| Duplicate check | ❌ missing |
| `shootCountChanged` emitted | ✅ RC2 adds `physical shot accepted: seq N (type)` |
| Shot added to model/session | ❌ missing |
| Shot rendered by QML | ❌ missing — **this is the gap that would size the latency** |
| Automatic feed requested | ✅ `paper feed requested: shot N … queued` |
| Feed started | ✅ `paper feed started: shot N duration X s` |
| Feed completed | ✅ `paper feed completed: shot N` |
| Serial scan / candidates | ✅ implemented — but never reached (SERIAL-AUTO-001) |

The log already carries millisecond stamps on every line, so **the missing
pieces are the events themselves, not the timing format**. Without a
frame-received stamp and a QML-rendered stamp, the observed latency cannot be
attributed to the serial read, the acceptance path, the model update, the
render, or the feed thread.

Note the feed command **blocks for the configured duration** to serialise motor
commands. If the render happens on the same turn of the event loop after that
call, a ~1 s feed could itself be the visible delay. That is a hypothesis, not
a finding — it needs the two missing timestamps to confirm or kill.
