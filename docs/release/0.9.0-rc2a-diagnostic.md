## 1. SERIAL-AUTO-001 — fixed

**Severity 2. Registered from the RC2 physical test, not inferred.**

### What actually happened

The field log (`%TEMP%\tachus_log01082026-145445.log`) shows:

```
14:54:48.164  connect with port number -> Auto Connect
14:54:48.187  Auto connecting to port number -> COM4
14:55:28.582  connect with port number manually -> COM4
```

and **zero** occurrences of `serial scan started`, `candidate`,
`auto-connect attempted` or `remembered target`. `HKCU\Software\TechAim` had no
`TargetDevice` group. The selector never executed.

### Root cause — failed stage 5, candidate application

The RC2 selector was correct, tested and reachable, but it was wired into the
**last-resort fallback** inside `connectedModbus()`. Before reaching it, the
function performed a speculative `changedConnect(true, "")`. With an empty port
name, `ModbusCommSettings` silently substituted the stored port, the connection
"succeeded" at the driver level, and the function returned before any scan ran.

Every automated test passed because they all called the selector directly. None
of them asserted the *order* in which the application calls it. That gap is the
real defect, and it is now closed by tests 35–43 in
`tests/reliability/tst_target_hardware.cpp`.

### The corrected contract — decide, then connect

`TachusWidget::connectedModbus()` now begins:

```cpp
const bool automaticPath = portName.isEmpty();
if (automaticPath) {
    const QString chosen = chooseStartupPort();
    if (chosen.isEmpty())
        return false;          // never fall through to a speculative connect
    portName = chosen;
}
```

Consequences, each pinned by a test:

- `changedConnect(true, "")` is **never** called on the automatic path.
- `ModbusCommSettings` can no longer substitute a port, because the port name
  handed to it is always concrete.
- The stored port is demoted to a **candidate**, read through the new
  `MainWindow::storedSerialPortName()`, and used only when it still appears in
  the *current* enumeration. A stale COM7 from a previous machine is discarded
  instead of being connected to.
- Every non-`AutoConnect` outcome returns an **empty** port, so there is nothing
  a caller could accidentally connect with.
- Manual COM selection is untouched: a non-empty `portName` skips the selector
  entirely and goes straight through, exactly as in RC1 and RC2.

### Operator-visible states

`targetStateChanged(state, portName)` now reports the scan honestly:

| State | Meaning |
|---|---|
| `SCANNING` | enumeration in progress |
| `TARGET DETECTED` | one confident candidate; connecting to it |
| `TARGET CONNECTED` | communication confirmed; fingerprint remembered |
| `MANUAL SELECTION REQUIRED` | several plausible adapters — the operator chooses |
| `TARGET NOT DETECTED` | no candidate; manual selection only |

The fingerprint is stored **only after communication is confirmed**, and only
if it still matches the device that was selected.

## 2. Shot-pipeline timestamps — SHOT DISPLAY LATENCY

Arnold observed a noticeable delay between the physical shot and the screen
response. RC2 had no way to say *where* that delay sat, so RC2a stamps the
pipeline instead of guessing at it. Enable developer mode
(`developer_mode=1`) and the log carries, per shot:

| Stamp | Side | Boundary |
|---|---|---|
| `decoded` | C++ | protocol frame validated and coordinates stored |
| `emit-shootCountChanged` | C++ | notification about to leave the backend |
| `qml-notified` | QML | the interface has received it |
| `qml-scored` | QML | ISSF ring score computed |
| `qml-marker-added` | QML | the impact has been added to the series |
| `zoom-requested` / `zoom-started` | QML | auto-zoom entry and animation start |
| `emit-returned` | C++ | control back in the backend |
| `feed-hook-enter` / `feed-hook-exit` | C++ | paper-feed decision window |

All stamps share one session tag and one monotonic clock, so the differences are
directly comparable. This is measurement only — **no timing, scoring or feed
behaviour is changed by it.**

## 3. AUTO-ZOOM — still UNVERIFIED (audited, deliberately not "fixed")

The authorisation allowed an auto-zoom fix only if the intended behaviour is
clear, the path is demonstrably not executing, and the correction is small and
isolated. The audit satisfies the first condition and **fails the second**, so
the status stays **AUTO-ZOOM — UNVERIFIED**.

What the audit found in `CenterPane.qml`:

- `autoZoomOn: true`, `autoZoomTarget: 2.4`, `autoZoomHold: 4` (≈4 × 450 ms
  ticks) — the feature is enabled by default.
- `triggerAutoZoom(px, py)` is defined at line 29 and called at line 333 from
  the shot-processing path.
- The call is gated by
  `trainingHidesImpact = shootingPage.isTrainingMatch && !TRAINING.showImpacts`.

**That gate is almost certainly the explanation, and it is correct behaviour.**
Arnold's test was a 10 m Air Rifle **Training** programme. In a Training
visibility mode that hides impacts, the athlete is *intended* not to see the
shot — so the face is not drawn and the view is not zoomed to it. Zoom
suppression there is the programme working, not a defect.

Two things are therefore unknown, and both need the physical test rather than
more reading:

1. which Training visibility mode was actually selected during the RC2 test;
2. whether auto-zoom runs in a **non-Training** discipline, where the gate does
   not apply.

Changing the gate now would risk revealing impacts that a Training programme is
designed to withhold — a much worse defect than a missing zoom. RC2a therefore
measures instead: `zoom-requested` proves the call site was reached, and the
absence of `zoom-started` after it proves the gate suppressed it. Test D below
settles it in one shot.

## 4. Physical test — RC2a

Extract to `C:\TechAim\RC2a\`. Do not overwrite `C:\TechAim\RC1\` or
`C:\TechAim\RC2\`.

Set `developer_mode=1` in `config.ini` for this test only. Keep
`app_mode=Live`.

### Test A — automatic detection with the target connected

1. Connect the target. Leave Bluetooth **on** (that is the failing condition).
2. Launch. Do not touch the COM selector.
3. Record the displayed target state and the port.

Pass: `TARGET DETECTED` then `TARGET CONNECTED` on the target's real port,
with no manual selection. Log shows `serial scan started` and at least one
`candidate`.

Fail: any Bluetooth port opened, or `TARGET NOT DETECTED` with the target
plugged in.

### Test B — restart uses the remembered adapter

Close and relaunch with everything unchanged. Pass: the log shows
`remembered target` and connects without a scan-wide search.

### Test C — target absent

Unplug the target, launch. Pass: `TARGET NOT DETECTED`, no connection claimed,
manual selection still available, **no paper movement**, no false shot.

### Test D — three shots, Training, impacts VISIBLE

Choose a Training visibility mode that **shows** impacts. Fire 3 shots.

Record for each shot: the stamp differences, whether the marker appeared,
whether the view zoomed, and whether the paper fed once.

Pass: one feed per shot, marker drawn, `zoom-started` present.

If `zoom-requested` appears but `zoom-started` does not *in this mode*, auto-zoom
is genuinely defective and becomes a registered defect with evidence.

### Test E — manual COM selection still works

Select the port by hand. Pass: connects exactly as in RC2 — the selector is
bypassed.
