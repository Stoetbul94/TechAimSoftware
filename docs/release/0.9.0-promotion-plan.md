# Tech Aim 0.9.0 — promotion plan

**Prepared, NOT executed.** Nothing in this document may be started before the
RC2a physical test has been performed and its evidence recorded.

**RC2a is not renamed to RC3.** RC3 is a **new build** from the approved source
commit with production settings. Renaming a diagnostic build would ship
`developer_mode` expectations and a diagnostic channel string into a deployment,
and would break the link between a package hash and how it was produced.

---

## Gate 0 — the physical test happens

Arnold runs [Physical-Qualification-Checklist.md](../deployment/Physical-Qualification-Checklist.md),
tests A–J, three shots, using `dist\RC2a-Physical-Retest-Pack\`.

Nothing below starts until the completed checklist and the diagnostic support
bundle are in hand.

**If it fails:** do not proceed. Register the defect with the physical evidence,
diagnose it, and treat the failure as authoritative over any automated result —
that is the lesson of SERIAL-AUTO-001.

---

## Step 1 — Record physical evidence

Store the completed checklist and the support bundle in
`docs/release/0.9.0-rc2a-field-test-results.md`, with:

- Windows edition, version, build, architecture
- the port chosen and whether Bluetooth was enabled (it must have been)
- the target state sequence observed
- per-shot latency, zoom observed, feed count
- the Training visibility mode used (decides the auto-zoom question)
- the support-bundle SHA-256

Record what happened, including anything that only partly worked.

## Step 2 — Close SERIAL-AUTO-001

Only if **tests A, B and C all passed**. Update:

- `docs/release/0.9.0-rc2-field-test-01-results.md` — status to **CLOSED**, with
  the physical evidence
- `docs/release/0.9.0-known-limitations.md` — limitation 3
- `docs/release/0.9.0-rc2a-diagnostic.md` — §1

A defect closes on physical evidence, never on code changes or a passing suite.

## Step 3 — Confirm paper feed still passes

From test D (no startup movement), E, F and H (exactly one feed per shot, and
the sighter feeding for the sighter duration). If feeding regressed, that is a
new defect and promotion stops.

## Step 4 — Assess the latency traces

From `shot-pipeline-stamps.txt`. Locate the delay:

| Interval | Meaning |
|---|---|
| `decoded` → `emit-shootCountChanged` | Backend processing |
| `emit-shootCountChanged` → `qml-notified` | Signal delivery |
| `qml-notified` → `qml-marker-added` | Scoring + draw |
| `feed-hook-enter` → `feed-hook-exit` | Paper-feed decision |

Also settle **auto-zoom**: `zoom-requested` present but `zoom-started` absent,
in a mode where impacts are **visible**, is a real defect. In a mode where
impacts are hidden it is correct suppression.

Whatever is found is **recorded, not fixed here** — a latency fix is a runtime
change and needs its own branch, tests and physical verification.

## Step 5 — Confirm reconnect and restart

Tests G, H and I. Reconnect must work without manual selection, no false shot,
no paper movement; restart must use the remembered adapter.

## Step 6 — Return developer_mode to 0

In Arnold's `C:\TechAim\RC2a\config.ini`, and confirm the RC3 build carries `0`.

`Verify-Deployment.ps1` defaults to `-ExpectDeveloperMode 0` and **fails** a
package carrying `1`, so this cannot be forgotten silently.

## Step 7 — Build RC3

A **new build**, not a rename.

1. Branch `release/0.9.0-rc3` from the approved commit (`4151620` plus whatever
   Steps 1–5 required, if anything).
2. Merge the deployment-preparation branch so the documents and tooling travel
   with it.
3. `APP_VERSION_STR = 0.9.0-RC3`; release channel back to
   **`Internal Field Test`** — the ` — Diagnostic` suffix must go.
4. `qmake Seta.pro`, delete `release/main.o`, `release/qrc_qml.cpp`,
   `release/qrc_qml.o` (the commit stamp is baked at qmake time and QML needs
   regeneration), then `mingw32-make -f Makefile.Release`.
5. Confirm the banner shows the RC3 commit — a stale build stamp has bitten
   before.

**Decide deliberately whether the diagnostic stamps stay.** They are gated
behind `developer_mode` and cost nothing when off; keeping them means the next
field problem is measurable instead of guessable. Recommendation: **keep them**.

Run the Qt console harnesses with the Qt `bin` on `PATH` **and**
`QT_QPA_PLATFORM=offscreen`. Never infer a pass from the exit code — capture the

## Step 9 — Run the deployment audit

```bash
python tests/release/check_deployment_package.py dist/TechAim-0.9.0-RC3-FieldTest-Windows-x64
```

Update the default package path in that script for RC3.

## Step 10 — Portable launch test

Launch the extracted folder with no Qt, no MinGW and no repository on `PATH`,
from its own working directory, and confirm it starts and stays running.

```bash
powershell -File tools\deployment\Verify-Deployment.ps1 -PackageDir <RC3 folder> -ExpectDeveloperMode 0 -ExpectVersion 0.9.0-RC3
```

Also re-run `Test-AppDataUpgrade.ps1` with RC2a as old and RC3 as new.

## Step 11 — Clean-machine test

**This is still blocked and must be resolved before deployment.** Use
[Clean-Machine-Test.md](../deployment/Clean-Machine-Test.md) on a machine that
has never had Qt or a compiler. Windows Sandbox needs Windows Pro or better —
the development machine is Home.

Do not convert an unperformed test into a pass.

## Step 12 — Calculate the new SHA-256

For the ZIP and the executable. Record both in the RC3 manifest and in the
release document. Re-verify the RC1, RC2 and RC2a hashes afterwards to prove
they were not disturbed.

## Step 13 — Final qualification kit

Assemble with `New-DeploymentPrep.ps1` and `New-RC2aRetestPack.ps1` (retargeted
to RC3), containing: the RC3 ZIP and checksum, the operator guide, known
limitations, the field-test notice, the qualification checklist, the support
tool, the verification script, and the rollback package **by reference with its
hash**.

Verify the kit with `Verify-Deployment.ps1` before it leaves the machine.

## Step 14 — Seek explicit deployment approval

Present: physical evidence, the closed defect, all suite results, the deployment
audit, the clean-machine result, hashes, and the remaining known limitations —
including every discipline still unqualified.

**Approval is a decision, not an output of this plan.** Until it is given
explicitly, the status stays:

```
NOT APPROVED FOR FINAL DEPLOYMENT
```

## Things that must not happen

- Renaming RC2a as RC3.
- Shipping a deployment build with `developer_mode=1`.
- Closing SERIAL-AUTO-001 on anything but physical evidence.
- Reporting the clean-machine test as passed from the development machine.
- Describing any artefact as code-signed, or claiming SmartScreen reputation.
- Claiming a discipline is qualified because its automated tests pass.
- Modifying, rebuilding or renaming RC1, RC2 or RC2a.

Not part of promotion; recorded so they are not lost:

|---|---|
| **LOG-001** — move logging to the AppData `Logs` directory | `%TEMP%` is cleared by Windows; evidence disappears |
| **CFG-001** — resolve `config.ini` against the executable directory | A wrong working directory silently loads defaults |
| **PKG-002** — diagnose the windeployqt failure | Deployment should not depend on a hand-maintained allow-list |
| **PKG-001** — rename `build-rc1-package.ps1` | It builds RC2a |
| Crash dump capture | A crash currently leaves almost nothing |
| Code-signing certificate | Removes the SmartScreen warning; required for any installer |
| Physical qualification of the remaining disciplines | Only one workflow has ever been tested on hardware |
